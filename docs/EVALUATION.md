# Evaluation contract v1 — no dataset or measured quality yet

This document defines evaluation inputs, the lexical runner, and metric arithmetic.
It contains no formal questions, relevance labels, benchmark runs, or quality
results. Tests use synthetic IDs only. Dataset creation remains a separate agreed
step; do not promote development examples into independent held-out evaluation.

## Dataset and labeling contract (schema implemented; no formal cases)

A future dataset must record dataset ID/version, repository snapshot ID, labeling
rules, size, label author/reviewer and review status, and limitations. Each case
needs a stable case ID, question, split (development/held-out), expected behavior
(supported/unsupported), relevance-label status, and relevant chunk IDs. Empty labels
alone do not establish that a question is unsupported; unlabelled and intentionally
unsupported cases must be distinguishable. No case records are created here.

All labels must resolve to the exact saved snapshot, whose IDs bind source/version/
chunking configuration. Do not run labels from a different snapshot or silently
map invalid IDs to similar text. Chunk-policy changes require label revalidation.
Document whether labels enumerate all relevant evidence; incomplete labels limit
recall interpretation. Distinguish finding any useful evidence from finding enough
evidence for a complete explanation. Human agreement on relevance is required
before claiming human-labeled or human-reviewed quality. Codex review is not
independent human validation. Never tune on held-out examples and then call them
independent evaluation without disclosing that use.

## Implemented input validation

`evaluation_inputs.validate_evaluation_input(raw_json, snapshot)` strictly parses
evaluation-input-v1 JSON using Pydantic, then checks exact snapshot identity and
chunk membership. Supply a snapshot from build_snapshot/load_snapshot. A partial
baseline is rejected; a complete degraded baseline remains eligible with its
warnings retained in the snapshot and runner report.

EvaluationDataset requires schema_version, dataset_id, dataset_version, snapshot_id,
labeling_rules, limitations, and a nonempty cases collection. Case IDs must be unique.
EvaluationCase requires case_id, question (nonblank, at most 2,000 characters), split
(development/held_out), expected_behavior (supported/unsupported/undetermined),
label_status (labelled/unlabelled), relevant_chunk_ids, label_author, review_status
(not_reviewed/codex_reviewed/human_reviewed), and reviewer. Unknown fields and wrong
types are rejected; strings are not silently normalized. Records are frozen.

Supported labelled cases require an author and at least one relevant ID. Explicitly
unsupported labelled cases require an author but no positive IDs. Unlabelled cases
must use undetermined expectation, no positive IDs/label author, and no review claim.
Reviewed cases require an explicit reviewer; unreviewed cases cannot name one.
Duplicate IDs, unknown chunk IDs, mismatched snapshots, malformed JSON, and future
schema versions are rejected without repair.

These checks establish consistency, not truth or reviewer identity. Declaring a
human review is not proof that one occurred; no human-review claim is generated by
this tool. Split metadata is retained but cannot prove a held-out case was never
seen during development. This function performs no I/O, freshness checks, retrieval,
or labeling. It accepts already supplied JSON; the bounded loader below limits
file input before parsing. The evaluation CLI below uses the same boundary. Tests use visibly
synthetic records, not formal questions or independent relevance labels.

## Observation/run contract and implemented Python runner

A run must record dataset/version/split and labeled case count; snapshot/schema
and file hashes/Git context; retrieval mode, tokenizer/ranking configuration, k;
model/version/settings when applicable; and execution environment. Embedding and
generation configuration are absent today and must not be fabricated.

Each observation records case ID, current/stale/unknown/error status, returned IDs
in rank order, diagnostic reasons, matched terms/scores, timing, and citation
validation outcomes. Search freshness must pass before returning evidence.
Blocked/error observations have no returned evidence, remain visible, and do not
receive success scores. Report attempted, successful-current, blocked, errored,
positively labeled, unsupported, and unlabelled case counts, plus denominator rules.
Do not hide failures by reporting only the cases that happened to run successfully.

## Implemented per-observation metrics

`evaluation.metrics_at_k(retrieved_ids, relevant_ids, k=..., status=...)` computes:

- hit_at_k: whether any of the first k IDs is labeled relevant.
- recall_at_k: distinct relevant IDs in the first k divided by the full relevant
  label count, including relevant evidence missed by retrieval.
- retrieved/relevant/matched counts for inspecting the calculation.

The cutoff is applied to the returned order before matching. Duplicate or malformed
IDs are rejected rather than deduplicated in a way that changes rank positions.
Fewer than k results are valid. A current empty result with positive labels is a
miss/zero recall. With no positive labels, hit/recall are undefined (None), not
perfect recall; unsupported behavior needs its separate recorded expectation.
Stale/unknown/error states are explicit and unscored (None), not zeros or successes.
Supplying evidence for those states is an error. The helper does not inspect files,
validate IDs against a snapshot, label relevance, time retrieval, or run a dataset.

Aggregate hit rate@k is the mean of per-case hits over current positively labeled cases,
with that eligible count disclosed alongside attempted/blocked/error counts. Aggregate
macro recall@k averages per-case recall over the same eligible cases. No eligible
cases means undefined metrics, never zero or 100%. The implemented summary helper follows these rules. Any later end-to-end reliability measure must state its denominator
and keep failed versus current-no-match outcomes distinguishable.

## Timing, citations, unsupported questions, and future answers

The Python runner uses a monotonic timer (perf_counter) to separately
record ranking-only time and per-case total time including snapshot reload/validation
and freshness reads. Include empty successful queries, record blocked/error timing
separately, document cold/warm conditions and corpus size, and do not compare one
mode's ranking-only latency with another's full-request latency. Report sample
counts and variability rather than pretending one run is representative.

The runner resolves every returned ID against the
validated saved snapshot and compares path, inclusive line range, exact text, and file hash;
freshness is a separate source-state check. Invalid references fail visibly; do
not repair them silently. These checks establish traceability, not relevance or
semantic correctness. Existing persistence checks are not an independent citation
evaluation report.

Unsupported-question behavior is separate: a lexical match can occur for an
unsupported question, and no lexical match cannot prove that evidence is absent.
Record observed behavior against an explicit expectation; do not infer calibrated
answerability from overlap scores. Future answers require separate schema validity,
citation-reference validity, model availability, and human-reviewed correctness
and sufficiency. No answering model or answer correctness evaluation exists now.

Freshness and refresh behavior already have software tests, including unknown,
stale, and interrupted-write cases. They are not benchmark results. The formal
dataset, representative timing measurements,
and human quality review remain future work. Do not add retrieval complexity based on invented gains.

## Bounded loader and lexical runner (Python API)

`evaluation_runner.load_evaluation_input(path, snapshot)` accepts a regular,
non-symlink file, reads at most 1,000,000 bytes plus one overflow probe, validates
its JSON/snapshot binding, and rejects more than 1,000 cases. It never creates
questions or labels. Caller-owned input files should stay outside indexed supported
source and remain private. JSON format is documented by the input models; no
populated example/formal dataset file is supplied.

`run_evaluation(snapshot_path, dataset_path, root, split=..., k=5)` requires explicit
development or held_out selection and k from 1–100. Input/setup failures raise
before queries. A selected split with no cases is an error. All provided records
are validated, but only selected cases execute and appear in the report. Total
input case count is separate; the report does not echo other-split questions.
Split fields are not access control: keep held-out data separate for stronger
isolation and do not claim independent evaluation after tuning on those cases.

The runner records shared setup_seconds for initial snapshot/input loading. Each
selected case then reloads and validates the saved snapshot, verifies its ID has
not changed, checks freshness, and ranks only current source. It separately records
ranking_seconds and total_seconds through reference checks and metric calculation.
Total per-case timing excludes shared setup, process startup, and report serialization;
it includes that case's snapshot reload. Do not call it whole-CLI wall-clock latency.
Blocked cases have no ranking time; errors can retain timing for a ranking phase
that completed before a later reference-check failure. Timings on synthetic fixtures
are not representative measurements or evidence of speed gains.

Returned references must be unique and match the validated snapshot's exact source
metadata; invalid references become error observations with no returned evidence
or metric score. citation_valid is None when no citations were checked, not an
invented perfect validity score. Per-case exceptions remain visible and later
cases continue; interrupts propagate. Stale/unknown observations remain unscored.
Current empty results with positive labels are misses; unsupported/unlabelled
cases have undefined hit/recall. Unsupported cases separately record whether
lexical matches occurred, without calling that calibrated answerability.

EvaluationRun retains dataset identity/provenance for the selected cases, the full
snapshot manifest (including hashes/Git/configuration/warnings), root, corpus size,
policies/runtime, setup time, and every selected observation. It is returned in
memory; no report is automatically saved, no snapshots refreshed, and no settings
are tuned. Aggregate summaries and the explicit CLI are available below. Tests and temporary
executions use synthetic schema/runner records only, with no retained formal data
or claimed quality result. No model is called or downloaded.

## Aggregate summaries (Python API)

`evaluation_summary.summarize_run(run)` accepts a runner-created EvaluationRun and
requires exactly one matching observation for every selected case. Missing or
repeated case records, inconsistent stored per-case metrics, invalid timings, or
inconsistent citation-count/validity populations are rejected rather than silently
changing denominators. The helper is pure: it never queries, reads, writes, labels,
or tunes. Preserve the detailed run alongside its summary for diagnosis.

The summary records dataset ID/version, total input case count, selected split,
snapshot ID, saved degraded state, k, and ranking/tokenization policies. Attempted
is the selected observation count, including all current/stale/unknown/error cases;
status counts sum to attempted. Supported/unsupported/unlabelled counts span all
attempted outcomes. Eligible is only current cases with positive relevance labels.
Hit count divided by eligible gives hit rate@k; mean per-case recall gives macro
recall@k. Macro recall is not pooled matched labels divided by pooled relevant
labels. Zero eligible cases means both metrics are None. Blocked/error cases remain
in attempted/status counts without becoming fabricated misses or successes.

Current explicitly unsupported cases and how many returned lexical matches are
counted separately. This is observed behavior, not an answerability probability or
a claim that no match proves no relevant evidence exists. Unlabelled cases do not
become implicitly unsupported or inflate recall.

Citation counts include checked observations and checked references, plus valid
and invalid observation counts. citation_observation_validity_rate divides fully
valid checked observations by all checked observations, including failures that
became errors. It is not a per-reference rate: a failed multi-reference observation
cannot identify exactly how many individual references failed. No checked
observations means None, not a perfect validity score. Current empty results and
blocked cases do not create citation-validity credit.

Timing populations are grouped by current/stale/unknown/error. Each total/ranking
summary provides count, minimum, mean, median, maximum; an empty group has count 0
and undefined statistics. Total times include successful no-match requests and
blocked/errors in their own groups. A ranking phase completed before a later error
can appear in the error group's ranking samples. Shared setup is retained in the
run, not repeatedly added to case times. No representative latency claim follows
from synthetic fixtures; record real corpus conditions and variability separately.

## Explicit evaluation CLI

`gitcontext evaluate ROOT --dataset INPUT --split development --top-k 5` invokes
bounded input loading, snapshot validation/binding, the selected-split runner, and
summary consistency checks. held_out is the other accepted split; neither split is
automatic. Output is evaluation-report-v1 JSON with run and summary. No dataset,
label, report file, settings change, or refreshed snapshot is created automatically.
User-directed stdout redirection is possible; reports contain private source and
provenance and must not be committed accidentally.

Exit 0 means current execution completed, even when hits/recall are zero or
undefined for a non-positive-label population. There is no automatic quality
threshold. Errors take exit 1; argument errors take exit 2; unknown source takes
exit 4 if there are no errors, otherwise stale source takes exit 3 if there are no
errors/unknowns. Per-case failures retain a full report. Invalid setup/input fails
before queries and returns an explicit error, not a fabricated run. Snapshot and
input files remain unchanged. This CLI does not validate that declared human
review happened, repair stale labels, or make held-out data independent by itself.
